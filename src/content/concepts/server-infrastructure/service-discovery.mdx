## The problem

Checkout needs Orders, but individual Orders instances are replaceable. Their IP addresses can change after deployments, rescheduling or failures.

Hard-coding one IP makes normal instance churn a client outage.

## Mental model

Separate **service identity** from **instance location**:

```text
stable identity: orders.service
runtime endpoint set:
  10.0.0.12:443
  10.0.0.19:443
```

The caller resolves the stable name, receives a set of current endpoints, and dials one endpoint. A TTL or watch mechanism controls how long that endpoint data is considered current.

<Callout title="An endpoint is disposable runtime data">
  Source code should depend on the service identity. Resolved IPs belong to the current deployment state and may disappear.
</Callout>

## Practical example

Kubernetes gives Services DNS names. A caller can use a Service name rather than a Pod IP. Other systems use service registries or DNS records populated by orchestration.

A stale endpoint window is normal in eventually refreshed discovery. Robust callers often combine discovery with connection errors, retries and load-balancing logic.

TTL is a trade-off:

- shorter TTL → fresher endpoint data, more resolution work;
- longer TTL → fewer resolutions, larger stale window.

Exact behavior depends on the resolver, client library and discovery mechanism.

## Failure modes and trade-offs

- **Hard-coded IPs** turn routine replacement into outage.
- **Stale cache** keeps dialing a removed endpoint.
- **Registry outage** prevents new resolutions even if existing connections still work.
- **Thundering refresh** makes many clients re-resolve at once.
- **No observability of resolved IP** makes connection failures difficult to diagnose.

Log both the logical service name and the concrete endpoint selected for each failed connection.

## Takeaway

Service discovery is **stable identity → current endpoint set → connection**. Treat endpoint addresses as temporary, observe stale-dial failures explicitly, and choose refresh behavior deliberately.
