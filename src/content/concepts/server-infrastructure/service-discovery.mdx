## مسئله

Checkout به Orders نیاز دارد ولی نمونه‌های Orders قابل جایگزینی هستند. IP پس از deploy، reschedule یا خرابی تغییر می‌کند. وابستگی به IP ثابت می‌تواند جایگزینی معمول نمونه را به قطعی کلاینت تبدیل کند.

## مدل ذهنی

هویت سرویس را از محل اجرای نمونه جدا کنید. کلاینت می‌تواند نام پایدار را حل کند، مقصد فعلی را انتخاب کند و اتصال برقرار کند. در برخی سازوکارها TTL یا watch مدت اعتبار داده کش‌شده را تعیین می‌کند.

```text
stable identity: orders.service
runtime endpoint set:
  10.0.0.12:443
  10.0.0.19:443
```

</Callout>

## آزمایش تعاملی

یک endpoint بعد از کش شدن حذف می‌شود. تفاوت معتبر ماندن نام و شکست اتصال به IP قدیمی را دنبال کنید.

## مثال عملی

Kubernetes Service می‌تواند نام DNS داشته باشد؛ نوع معمول Service به IP مجازی و نوع headless می‌تواند به IP نمونه‌ها حل شود. سیستم‌های دیگر registry یا DNS مدیریت‌شده دارند. کلاینت مقاوم discovery را با مدیریت خطای اتصال، retry محدود و توزیع بار ترکیب می‌کند.

TTL کوتاه داده تازه‌تر و هزینه حل بیشتر، TTL بلند هزینه کمتر و پنجره داده قدیمی طولانی‌تر دارد. رفتار دقیق به resolver، کتابخانه کلاینت و سازوکار discovery وابسته است.



## خطاهای رایج و ملاحظات

- IP ثابت: جایگزینی عادی باعث قطعی می‌شود.
- کش قدیمی: اتصال به endpoint حذف‌شده.
- خرابی registry: حل نام جدید ممکن نیست حتی اگر اتصال قبلی زنده باشد.
- refresh هم‌زمان کلاینت‌ها باعث بار ناگهانی می‌شود.
- بدون ثبت IP منتخب، تشخیص خطای اتصال دشوار است.

نام منطقی سرویس و مقصد واقعی هر اتصال ناموفق را ثبت کنید.
