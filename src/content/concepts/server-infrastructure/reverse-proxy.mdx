## The problem

A browser calls `https://api.example.com/api/orders`. The client should not need to know whether Orders currently runs on port 8080, three containers, or a different internal host tomorrow.

A Reverse Proxy creates a stable public edge. It receives the public connection, applies edge-level policy and forwards the request to the selected internal upstream.

## Mental model

Follow one concrete request:

```http
GET /api/orders HTTP/1.1
Host: api.example.com
Accept: application/json
```

A simple route table might be:

```text
/api/*  → API :8080
/app/*  → Web :3000
```

The proxy can terminate TLS and inspect the Host and Path needed for routing. The API still owns order validation, pricing and persistence.

<Callout title="Edge policy, not domain ownership">
  TLS termination, routing, coarse access policy and timeouts are natural edge concerns. Order pricing or inventory rules belong to the service that owns those concepts.
</Callout>

## Practical example

A minimal NGINX-style configuration can express the same idea:

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://api:8080;
    }

    location /app/ {
        proxy_pass http://web:3000;
    }
}
```

This snippet is illustrative. Production configuration also needs appropriate headers, timeout policy, TLS configuration, logging and upstream health strategy.

If `/api/orders` matches the API route but the proxy cannot establish the upstream connection, the proxy can return **502 Bad Gateway**. That is different from the API successfully receiving the request and intentionally returning a 4xx or 5xx application response.

## Failure modes and trade-offs

- **Wrong route rule.** A valid request reaches the wrong upstream or no upstream.
- **Bad timeout policy.** Too short causes false failures; too long ties up edge resources.
- **Unhealthy upstreams remain eligible.** The proxy keeps forwarding to targets that cannot serve.
- **The edge becomes a bottleneck.** TLS, buffering and routing consume real resources.
- **Business logic drifts into the proxy.** Ownership becomes difficult to test and evolve.

Useful signals: edge P99, upstream connection failures, upstream response status distribution, healthy upstream count and route-level request volume.

## Takeaway

A Reverse Proxy is a **public boundary plus an upstream-selection decision**. Trace the concrete request: receive → terminate TLS → inspect metadata → match rule → forward → relay response. Keep business behavior behind that boundary.
