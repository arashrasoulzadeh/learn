## مسئله

مرورگر به https://api.example.com/api/orders درخواست می‌دهد. نباید لازم باشد بداند Orders اکنون روی پورت 8080 یا چند کانتینر اجرا می‌شود. Reverse Proxy مرز عمومی پایدار فراهم می‌کند، سیاست لبه را اعمال می‌کند و درخواست را به upstream منتخب می‌فرستد.

## مدل ذهنی

درخواست واقعی زیر را دنبال کنید. پراکسی می‌تواند TLS را خاتمه دهد و Host و Path لازم برای مسیریابی را بخواند. اعتبارسنجی سفارش، قیمت و ذخیره‌سازی همچنان مسئولیت سرویس API هستند.

```http
GET /api/orders HTTP/1.1
Host: api.example.com
Accept: application/json
```

```text
/api/*  → API :8080
/app/*  → Web :3000
```

<Callout title="سیاست لبه، نه مالکیت منطق دامنه">
  TLS termination، مسیریابی، سیاست دسترسی سطح لبه و timeout می‌توانند مسئولیت پراکسی باشند. قوانین قیمت و موجودی در سرویس مالک دامنه باقی می‌مانند.
</Callout>

## مثال عملی

پیکربندی NGINX زیر فقط مثال آموزشی است. در محیط واقعی به گواهی و کلید TLS، headerهای مناسب، timeout، logging و راهبرد سلامت upstream نیز نیاز دارید.

اگر /api/orders با مسیر API منطبق باشد اما اتصال به upstream برقرار نشود، پراکسی می‌تواند 502 Bad Gateway برگرداند. این با پاسخ عمدی 4xx یا 5xx از برنامه‌ای که درخواست را دریافت کرده متفاوت است.

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    location /api/ {
        proxy_pass http://api:8080;
    }

    location /app/ {
        proxy_pass http://web:3000;
    }
}
```

## خطاهای رایج و ملاحظات

- قانون مسیر اشتباه: درخواست به مقصد نامناسب می‌رسد.
- timeout کوتاه یا بلند نامناسب: خطای کاذب یا اشغال منابع.
- upstream ناسالم هنوز مجاز است.
- مصرف TLS، buffering و routing در لبه گلوگاه می‌شود.
- انتقال منطق دامنه به پراکسی، آزمون و تغییر مالکیت را دشوار می‌کند.

P99 لبه، خطاهای اتصال upstream، توزیع status، تعداد مقصد سالم و حجم درخواست هر مسیر را پایش کنید.

## جمع‌بندی

Reverse Proxy مرز عمومی و نقطه تصمیم انتخاب upstream است: دریافت، پایان TLS، بررسی metadata، انتخاب مسیر، ارسال و بازگرداندن پاسخ.
