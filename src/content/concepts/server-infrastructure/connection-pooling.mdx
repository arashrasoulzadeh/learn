## مسئله

ساخت اتصال پایگاه داده می‌تواند TCP، TLS، احراز هویت و تخصیص نشست سمت سرور داشته باشد. ساخت اتصال برای هر HTTP request تأخیر و خطر طوفان اتصال ایجاد می‌کند. استخر تعداد محدودی اتصال آماده را میان کارها به اشتراک می‌گذارد.

## مدل ذهنی

چرخه را به صورت قرض گرفتن، اجرای query، بازگرداندن و استفاده مجدد ببینید. استخر چهار اتصال چهار جایگاه دارد. اگر همه مشغول باشند، درخواست بعدی باید مطابق سیاست منتظر بماند، timeout شود یا رد شود؛ اتصال نامحدود محدودیت ظرفیت را از بین می‌برد.

```text
borrow → query → return → reuse
```

## آزمایش تعاملی

درخواست‌های A تا E چهار اتصال شماره‌دار را به اشتراک می‌گذارند؛ استفاده مجدد از اتصال ۱ و انتظار E را مشاهده کنید.

## مثال عملی

اگر PostgreSQL برای مجموعه برنامه ۲۰۰ نشست اختصاص دهد و ۲۰ نمونه App هر کدام استخر ۲۰تایی داشته باشند، حداکثر نظری ۴۰۰ اتصال است؛ دو برابر بودجه. نقطه شروع اندازه‌گیری، بودجه اتصال تقسیم بر بیشینه تعداد نمونه‌هاست. اتصال مدیریتی رزرو، برنامه‌های دیگر، مدت تراکنش و هدف صف را هم لحاظ کنید.

استخر می‌تواند درون فرایند یا بیرونی باشد. Transaction pooling و session pooling معناهای متفاوتی دارند؛ فرض نکنید prepared statement، جدول موقت و session variable در همه حالت‌ها رفتار یکسان دارند.

```text
per-instance pool budget
≈ database connection budget / maximum App instance count
```

## خطاهای رایج و ملاحظات

- استخر بیش از حد بزرگ: فشار حافظه و scheduler و طوفان اتصال.
- استخر کوچک: انتظار با وجود ظرفیت آزاد پایگاه داده.
- تراکنش طولانی یا اتصال بازنگشته: سایر درخواست‌ها گرسنه می‌مانند.
- نبود timeout برای checkout: انتظار نامحدود.

تعداد اتصال مشغول، زمان انتظار، نرخ checkout timeout و نشست‌های فعال پایگاه داده را پایش کنید.
