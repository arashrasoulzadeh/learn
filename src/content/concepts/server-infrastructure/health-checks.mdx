## The problem

An application process can be running while being unable to serve a correct user request.

If App 2 needs a critical database and that database is unavailable, restarting the App process may not help. What matters for traffic is whether the instance is **ready** to serve.

## Mental model

Use different questions for different probes:

```text
/live  → Is this process alive enough to keep running?
/ready → Should new user traffic be routed here right now?
```

A possible state after a database failure is:

```http
GET /live  → 200 OK
GET /ready → 503 Service Unavailable
```

<Callout title="Probe semantics matter more than endpoint names">
  Liveness and readiness are roles. The exact endpoint names and implementation are choices. Design the check around the action the platform will take when it fails.
</Callout>

## Practical example

A readiness handler can test whether the process has initialized and whether dependencies required for its primary request path are usable.

Be careful with deep dependency checks. If every App instance probes the same database aggressively, the health mechanism itself can add load. If a non-critical analytics dependency fails, making the entire service unready might reduce availability unnecessarily.

Kubernetes uses readiness probes to decide whether a Pod should receive Service traffic. Liveness probes are used for container restart decisions. Startup probes can protect slow-starting workloads from premature liveness failures.

## Failure modes and trade-offs

- **Shallow probe:** always returns 200 even when the instance cannot serve.
- **Overly deep probe:** one optional dependency removes every instance.
- **Flapping:** thresholds are too sensitive to brief latency spikes.
- **Probe storm:** many instances run expensive checks too frequently.
- **Liveness depends on the same failing external system:** restarts amplify an external outage.

Monitor ready target count, probe failure reasons, routing-set churn and user-visible error rate.

## Takeaway

Health is not one boolean. Define the question, the probe and the action together. **Liveness protects process recovery; readiness protects user traffic.**
