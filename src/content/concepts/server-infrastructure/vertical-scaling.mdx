## The problem

A host with **2 CPU / 8 GB** is saturated by an **8 requests/s** workload. Making that same machine larger can be a valid fix—but it solves a different problem from adding redundancy.

## Mental model

Vertical scaling changes resources **inside one failure domain**.

In this model:

```text
Before: 2 CPU / 8 GB  → capacity 4 req/s
After:  8 CPU / 32 GB → capacity 12 req/s
Workload: 8 req/s in both cases
```

The workload stays constant so the effect of resizing is visible.

<Callout title="Bigger is not redundant">
  Headroom answers “can this machine do more work?” Redundancy answers “can the service continue if this machine disappears?” They are separate dimensions.
</Callout>

## Practical example

Vertical scaling is common for databases and stateful systems where distributing state is a larger architectural change than resizing a machine.

A cloud VM might be stopped and resized to a larger instance type. A container platform might increase CPU and memory requests/limits. In either case, verify whether the workload can use the added resources: a single-threaded bottleneck may not benefit from more CPUs, and memory growth may only delay an unbounded leak.

The teaching model shows P99 improving from 240 ms to 70 ms. Those numbers are illustrative, not a benchmark. In production, measure your own latency before and after the change.

## Failure modes and trade-offs

- **Hardware ceiling.** There is always a largest practical instance.
- **Maintenance can still interrupt one node.**
- **A single failure domain remains.**
- **The workload cannot use the extra resource.** More CPUs do not fix serialization or a remote dependency.
- **Cost jumps in large steps.** Bigger instances can be less flexible than several smaller workers.

## Takeaway

Vertical scaling is **more resources in the same machine**. It can buy headroom quickly, but it does not automatically create high availability. Measure performance and failure domains separately.
